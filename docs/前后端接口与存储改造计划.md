# Smart CTO 前后端接口与存储改造计划

## 1. 目标

本计划用于支撑以下改造目标：

1. 当前前端项目从“纯前端 + 本地存储 + 直连大模型”演进为“前端 + 后端服务 + 数据库存储”。
2. 当前前端代码需迁移到独立 `frontend/` 目录，后续新增 `backend/` 目录承载服务端代码。
3. 前后端使用统一的数据模型、接口语义和任务状态机，避免后续重复返工。
4. 业务能力保持与当前页面一致，优先保证 `Home -> ProblemDetail -> Tools` 主链路可平滑迁移。

## 2. 当前系统现状

### 2.1 当前前端目录现状

当前项目本质上是单体前端工程，主要业务都在 `src/` 下：

- `src/views/HomeView.vue`
  - 数字化问题输入
  - 调用大模型解析客户基础需求
  - 创建“问题跟进项”
- `src/views/ProblemDetailView.vue`
  - 15 个任务节点的对话式推进
  - 回退、重置、重启当前任务
  - 沟通历史
  - 工作区卡片数据联动
- `src/views/DetailView.vue`
  - 企业分析详情
  - BMC、价值流等展示
- `src/views/ToolsView.vue`
  - 工具知识库主题、沉淀、讨论
- `src/views/TaskTrackingView.vue`
  - 目前仍是占位页，尚未形成完整业务
- `src/stores/analysis.ts`
  - 企业分析查询和保存
- `src/stores/problem.ts`
  - 数字化问题跟进列表和详情当前项
- `src/utils/storage.ts`
  - 当前所有核心业务数据均落在 `localStorage`
- `src/utils/toolKnowledge.ts`
  - 工具知识库的业务逻辑封装
- `src/api/ai.ts`
  - 当前直接从前端调用 DeepSeek

### 2.3 当前接口调用现状

当前对外调用主要分为两类：

#### A. 企业分析接口

文件：

- `src/stores/analysis.ts`

当前调用：

- `POST VITE_API_URL`
  - 用于查询企业分析结果
- `POST VITE_VALUE_STREAM_API_URL`
  - 用于查询价值流列表

问题：

- 由前端直接调用远端服务
- 没有统一后端聚合层
- 请求/响应结构未沉淀成共享契约

#### B. 大模型接口

文件：

- `src/api/ai.ts`
- `src/views/HomeView.vue`
- `src/views/DetailView.vue`
- `src/views/ProblemDetailView.vue`
- `src/utils/toolKnowledge.ts`

当前调用：

- 由前端直接使用 `fetchDeepSeekChat`
- 前端直接持有模型地址、模型名、API Key 读取逻辑

问题：

- API Key 不应长期暴露在前端链路
- 无法统一做日志、审计、限流、重试、超时控制
- 无法沉淀任务级调用策略

### 2.4 补充：`frontend/` 静态工程下的存储与首屏（2026-03）

> 说明：与上文以 `src/`（Vue）为主线的描述并行，仓库中 **`frontend/`** 为当前主力静态页实现；存储已支持 **local + IndexedDB** 与 **online + HTTP 适配器**。

| 场景 | 要点 |
|------|------|
| **local + IndexedDB** | `js/storage-indexeddb-adapter.js` 将原 `localStorage` 业务键迁移至 IndexedDB；`init()` 异步结束后通过 `setTimeout(0)` 派发 `storageIndexedDbReady`。`main.js` 监听后再次执行 `renderProblemFollowList()`（并可重载工具知识），避免刷新后短时仍读到「已清空 localStorage」的空缓存。 |
| **online + HTTP** | `js/storage-http-adapter.js` 与后端同步问题单与聊天；`storageBackendReady` 用于后端缓存就绪后的首页列表等重绘。 |
| **痛点标注（task6）** | `updateDigitalProblemPainPointSessions`、`updateDigitalProblemPainPointStep` 在启用适配器时**必须**经 `storage.js` 的 `adapter.updateDigitalProblem`（`upd`）合并写入 `digitalProblems`，与 `getDigitalProblems()` 同源；**禁止**仅写 `localStorage` 而绕过适配器缓存，否则单步/自动顺序执行会误判 `painPointSessions` 进度（例如仅跑一环即弹出「确认所有」）。 |

## 4. 需要接口改造的业务清单

以下按业务模块梳理。

### 4.1 首页数字化问题解析与跟进列表

页面：

- `src/views/HomeView.vue`

当前行为：

1. 用户输入客户问题
2. 前端直接调用大模型解析结构化字段
3. 前端直接写入 `digital_problem_followups`
4. 首页从本地读取列表

需要改造为：

1. `POST /api/problem-cases/parse`
   - 输入原始问题描述
   - 后端调用模型
   - 返回解析结果
2. `POST /api/problem-cases`
   - 创建问题跟进项
3. `GET /api/problem-cases`
   - 获取问题跟进列表
4. `DELETE /api/problem-cases/:caseId`
   - 删除问题跟进项
5. 可选：`GET /api/problem-cases/:caseId`
   - 获取单个问题详情

重点字段：

- `id`
- `createdAt`
- `customerName`
- `customerNeedsOrChallenges`
- `customerItStatus`
- `projectTimeRequirement`
- `currentMajorStage`
- `completedStages`
- `workflowAlignCompletedStages`
- `itGapCompletedStages`

### 4.2 企业分析查询与保存

页面/Store：

- `src/stores/analysis.ts`
- `src/views/DetailView.vue`

当前行为：

1. 前端直接请求企业分析服务
2. 前端直接请求价值流服务
3. 查询结果写入本地 `company_analyses`

需要改造为：

1. `POST /api/company-analyses/query`
   - 输入公司名称
   - 返回基础信息、BMC、元数据
2. `POST /api/company-analyses/value-streams`
   - 输入公司名称
   - 返回价值流列表
3. `POST /api/company-analyses`
   - 保存企业分析记录
4. `GET /api/company-analyses`
   - 列表查询
5. `GET /api/company-analyses/:analysisId`
   - 详情查询

建议统一返回结构：

- `basicInfo`
- `bmc`
- `metadata`
- `valueStreams`
- `storedAt`

### 4.3 问题详情主业务链路

页面：

- `src/views/ProblemDetailView.vue`

这是当前最重的模块，也是后端化改造的核心。

#### 当前前端承担的职责

1. 任务状态机推进
2. 聊天区消息管理
3. 结果卡生成
4. 工作区数据落盘
5. 回退/重置/重启当前任务
6. 沟通历史归档
7. Ask/Agent 模式差异控制
8. 任务上下文拼装
9. 模型调用

#### 建议拆出的后端能力

##### A. 主记录接口

- `GET /api/problem-cases/:caseId`
  - 获取问题主记录
- `PATCH /api/problem-cases/:caseId`
  - 更新主记录基础字段

##### B. 任务状态接口

- `GET /api/problem-cases/:caseId/tasks`
  - 获取 15 个任务节点状态
- `POST /api/problem-cases/:caseId/tasks/:taskId/start`
  - 启动任务
- `POST /api/problem-cases/:caseId/tasks/:taskId/complete`
  - 完成任务
- `POST /api/problem-cases/:caseId/tasks/:taskId/restart`
  - 重启当前任务
- `POST /api/problem-cases/:caseId/tasks/:taskId/rollback`
  - 回退到指定任务
- `POST /api/problem-cases/:caseId/reset`
  - 重置到初步需求状态

##### C. 对话接口

- `GET /api/problem-cases/:caseId/messages`
  - 获取聊天记录
- `POST /api/problem-cases/:caseId/messages`
  - 发送消息
  - 支持 `mode=ask | agent`
  - 支持 `feedbackType=discussion | modification | normal`
- `DELETE /api/problem-cases/:caseId/messages/:messageId`
  - 删除消息，并触发相关状态回滚

##### D. 结果卡接口

- `POST /api/problem-cases/:caseId/tasks/:taskId/generate`
  - 生成任务结果
- `POST /api/problem-cases/:caseId/tasks/:taskId/confirm`
  - 确认结果卡
- `POST /api/problem-cases/:caseId/tasks/:taskId/revise`
  - 修正当前结果
- `POST /api/problem-cases/:caseId/tasks/:taskId/discuss`
  - 讨论当前结果

##### E. 沟通历史接口

- `GET /api/problem-cases/:caseId/history`
  - 返回任务树 + 过程日志

**与当前静态前端对齐（文档）**：侧滑沟通历史含**任务详情 / 过程日志 / 任务Skill** 三 Tab；过程日志的标签与汇总区、**任务Skill** 时间线与黄卡快照等 UI 规范见 `frontend/数字化问题跟进阶段设计.md` §0.6、`frontend/对话模型管理.md` §4.5–4.6；标签统一字号等为前端 `styles.css`（`.problem-detail-history-panel` 下 `--history-label-fs` 等），后端接口仅需返回结构化消息（含任务摘要中 `skillTimeline` 等），由前端按同一规则渲染。

#### 特别说明

`ProblemDetailView.vue` 当前既承担 UI，又承担业务编排。后端落地后应把以下逻辑迁走：

- `buildTaskContext`
- `buildProblemAfterRollback`
- `advanceTask`
- 各任务结果卡落库规则
- 删除消息后的回滚逻辑
- 任务完成后阶段推进逻辑
- Ask/Agent 调度规则

前端只保留：

- 视图状态
- 当前输入态
- 当前展开/折叠态
- 当前浏览阶段

## 6. 字段统一建议

当前项目同时存在驼峰和下划线字段混用的问题。

建议统一规则：

- 前端内部使用驼峰
- 后端 DTO 明确约束
- 数据库存储使用下划线
- 前后端交互优先使用驼峰

重点统一字段：

- `customerName`
- `customerNeedsOrChallenges`
- `customerItStatus`
- `projectTimeRequirement`
- `currentMajorStage`
- `workflowAlignCompletedStages`
- `itGapCompletedStages`

不建议继续在前端长期兼容以下老字段：

- `customer_name`
- `customer_needs_or_challenges`
- `customer_it_status`
- `project_time_requirement`

这些老字段只建议保留在迁移脚本或兼容层中。

## 7. 大模型接入改造建议

当前问题：

- 前端直连大模型
- 无法统一审计和失败治理

建议改造为：

- 前端不再直接调用 DeepSeek
- 后端提供统一 AI 编排层

建议后端提供至少 3 类能力：

1. 通用问答接口
   - 给 Ask 模式使用
2. 任务编排接口
   - 给 Agent 模式使用
3. 工具知识库 AI 接口
   - 给 Tools 页使用

建议保留任务级 trace 信息：

- `caseId`
- `taskId`
- `mode`
- `promptVersion`
- `model`
- `usage`
- `durationMs`
- `requestId`

## 8. 推荐迁移顺序

### 阶段 1：目录整理

1. 新建 `frontend/`
2. 将当前 Vite 项目整体迁入 `frontend/`
3. 预留 `backend/`
4. 修正构建、路径、环境变量

交付标准：

- `frontend` 独立可运行
- `npm run build` 通过

### 阶段 2：后端骨架

1. 搭建后端工程
2. 建立数据库连接
3. 先建基础实体表
4. 暂时保留假数据或本地 JSON 适配层

交付标准：

- 后端可启动
- 数据库可连通

### 阶段 3：首页和企业分析先接后端

优先原因：

- 依赖链较短
- 风险最可控

先落：

- 首页解析
- 问题案例列表
- 企业分析查询
- 企业分析保存

交付标准：

- 首页创建案例不再依赖本地存储
- 企业分析列表和详情可从后端读取

### 阶段 4：ProblemDetail 主链路落库

这是核心阶段。

先落：

- 主记录
- 聊天记录
- 任务状态
- 结果卡确认

后落：

- 回退
- 重启
- 删除消息回滚
- 沟通历史

交付标准：

- 页面刷新后状态完全来自后端
- 不再依赖 `localStorage`

### 阶段 5：Tools 页接后端

先落：

- 主题列表
- 主题沉淀内容
- 工具聊天

交付标准：

- Tools 页数据跨设备可复用

### 阶段 6：清理本地存储依赖

完成后清理：

- `StorageService` 主业务能力
- 页面中的本地回退逻辑
- 前端直连模型能力

最终仅保留：

- 临时 UI 状态
- 极少量缓存态

## 11. 风险与注意事项

1. `ProblemDetailView.vue` 当前业务编排过重，不能一次性全拆，建议按“消息 -> 任务状态 -> 结果卡 -> 回退”顺序分层迁移。
2. 当前部分中文文案和旧字段仍存在历史兼容逻辑，迁移时必须先冻结字段标准，再写数据库表。
3. 回退、删除消息、重启当前任务这三类动作都不是简单 CRUD，必须走事务或原子更新。
4. Ask/Agent 模式不能只做一个普通聊天接口，必须保留任务上下文和任务态。
5. 若明天就开始后端接入，建议先不要继续扩大前端本地逻辑，以免产生第二套状态源。

## 12. 结论

当前项目已具备较完整的前端业务形态，但状态源仍是：
