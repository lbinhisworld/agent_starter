## 2. 任务目标

- 建立 ProblemDetail fixture 的稳定命名规则和目录结构合同。
- 固定 `fixture_id`、`fixture_version` 与最小文件集合。
- 为 selector / DOM 对照与双渲染验证提供可复现输入。

## 3. 当前事实

- B 线要验证逻辑和 UI 一致，不能直接依赖在线活案例。
- 若 fixture 没有稳定命名与目录结构，双渲染结果就无法追溯到同一输入。
- fixture 本质上是验收输入快照，不是临时调试文件。
- 当前 online 详情刷新实际由 detail / messages / tasks 三段输入在前端组装；fixture 若不明确“哪份文件承载哪类输入”，后续 selector 与 DOM 对照仍会各自补字段。
- 本专项已冻结 B 线为 online-only，因此 fixture 也必须明确来源于 online 详情链，而不是 local 存储快照。

## 4. In Scope

## 5. Out Of Scope

## 7. 实施说明

1. 固定 `fixture_id` 和 `fixture_version` 的命名与升级规则。
2. 规定每个 fixture 至少包含 `case.json`、`messages.json`、`meta.json`，并写清各自承载的输入边界。
3. 把 fixture 目录结构写成合同，保证 selector、DOM、双渲染都能复用。
4. 明确 fixture 是对照输入真相源，不允许在验收时临时拼接或在线回源补数据。

### 7.1 fixture 根目录与层级合同

| 项 | 固定口径 |
| --- | --- |
| fixture 根目录 | `docs/plans/problem-detail-build-obfuscation-and-vue-unification/fixtures/problem-detail/` |
| 场景层级 | `fixtures/problem-detail/<fixture_id>/` |
| 版本层级 | `fixtures/problem-detail/<fixture_id>/<fixture_version>/` |
| 读取原则 | selector 对照、DOM 对照、双渲染流程都只读取同一版本目录下的文件，不跨版本拼接 |
| 来源模式 | 固定为 online-only 详情输入快照；不得混入 local 模式数据 |

### 7.2 `fixture_id` / `fixture_version` 命名规则

| 字段 | 规则 | 示例 | 固定口径 |
| --- | --- | --- | --- |
| `fixture_id` | 小写 kebab-case，统一以前缀 `pd-online-` 开头，后接场景语义 | `pd-online-task1-prelim-base` | 表示“是什么场景”，在同一场景跨版本保持不变 |
| `fixture_version` | 统一使用三位序号 `v001`、`v002`、`v003` | `v001` | 表示“同一场景的第几版输入快照”，不携带临时人名或日期口径 |

版本升级规则：

1. 只要 `case.json`、`messages.json` 或 `meta.json` 中会影响 selector / DOM / 双渲染结论的输入发生变化，就必须升级 `fixture_version`。
2. 仅修正文档注释、说明文字、额外备注，不改输入快照时，不升级 `fixture_version`。
3. 不允许覆盖旧版本目录内容；必须保留旧版本，供历史差异回溯。

### 7.3 最小文件集合合同

| 文件 | 必须承载的内容 | 禁止做法 |
| --- | --- | --- |
| `meta.json` | `fixture_id`、`fixture_version`、`capture_mode: \"online\"`、`scenario`、`source_commit`、`source_entry: \"index.html?caseId=\"`、`created_at`、`notes` | 只写标题，不记录版本与来源 |
| `case.json` | 单案例详情快照真相源；必须足以表达当前 case 级输入，包括 case 基本信息、任务相关 case 字段以及供 host/selector 还原详情快照所需的 case 级数据 | 只存 caseId 或只存裁剪后的展示字段，导致后续还要在线补拉 |
| `messages.json` | 与该 case 对齐的消息/过程日志数组，顺序固定，作为聊天与历史侧栏投影输入 | 只保留“最终展示文案”，丢掉消息结构、type 或顺序 |

补充固定口径：

1. `case.json` 是 case 级快照真相源，不等于“只存一个后端原始 item”；其内容必须足以支撑 host/selector 重建详情输入。
2. 首批最小文件集合不新增 `tasks.json`；若后续需要额外 sidecar，只能作为可选扩展文件，不能替代 `case.json` / `messages.json` / `meta.json`。
3. 双渲染正式验收只以这三份文件为必备输入，不接受临时再加在线 API 请求兜底。

### 7.4 目录示意与可选扩展

```text
docs/plans/problem-detail-build-obfuscation-and-vue-unification/
└── fixtures/
    └── problem-detail/
        └── pd-online-task1-prelim-base/
            ├── v001/
            │   ├── meta.json
            │   ├── case.json
            │   └── messages.json
            └── v002/
                ├── meta.json
                ├── case.json
                └── messages.json
```

可选扩展规则：

1. 允许在版本目录下增加 `notes.md`、`artifacts/`、`screenshots/` 等辅助文件。
2. 可选扩展只能补充证据，不能替代最小三件套。
3. 若扩展文件与最小三件套内容冲突，以 `meta.json` / `case.json` / `messages.json` 为准。

### 7.5 fixture 使用合同

| 使用方 | 固定要求 |
| --- | --- |
| `FE-20260411-18` | 覆盖集合必须基于本卡定义的 `fixture_id` / `fixture_version` 命名，不再另起编号体系 |
