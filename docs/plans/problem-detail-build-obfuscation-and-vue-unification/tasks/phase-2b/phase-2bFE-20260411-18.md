2. 把新建案例、task1、工作流对齐、task8、task10/task11 修改链列为首批必备集合。

### 7.2 `task1` 场景拆分原则

| fixture_id | 为什么必须单列 | 最低要求 |
| --- | --- | --- |
| `pd-online-task1-prelim-base` | 证明 task1 起步态、基础工作区与最小聊天链不漂移 | 必须保留基础 view/json/历史详情三 Tab 与 task1 当前态 |
| `pd-online-task1-prelim-supplement-merged` | 证明 `+需求` 后补充提炼与 merge 会改变 selector / DOM，而不只是多几条聊天消息 | 必须包含补充后 `preliminaryReq` 变化和跟进链 |
| `pd-online-task1-prelim-entity-buckets` | 证明最新高风险扩展链路全部被覆盖，而不是停留在旧 happy path | 必须包含核心对象、状态逻辑 entity buckets、逐条转移摘要、人员组织，必要时含历史详情删除结果 |

### 7.4 首批不单列 fixture 的范围

1. task2 / task3 / task5 / task6 / task7 / task9 / task12 / task13 / task14 / task15 首批不单独建 fixture，除非后续 selector / DOM 对照发现其风险无法被现有场景覆盖。
2. local 模式输入、离线存储、第二公开入口、独立 Vue 业务重写场景不进入首批 fixture 集合。
3. 若后续新增 fixture，必须复用本卡的优先级与命名体系，不得另起一套“补充样例”编号。

### 7.5 覆盖集合的使用顺序

1. `pd-online-shell-new-case-empty` 作为壳层最小冒烟 fixture，先跑。
2. 三张 task1 fixture 连跑，用于吃掉首批最复杂的语义恢复风险。
3. `pd-online-workflow-align-active` 与 `pd-online-task8-itgap-supplement` 用于验证跨阶段推进与中段工作区输入。
4. `pd-online-history-sidebar-rich` 单独作为历史侧栏结构级对照基线。
5. `pd-online-task10-role-permission-modify` 与 `pd-online-task11-core-business-object-modify` 作为高风险修改链收尾。

## 9. 验收边界

### 9.1 完成结果

- 首批 fixture 至少覆盖新建案例、task1、工作流对齐、task8、task10/task11 修改链。
- `task1` fixture 不再只有单一 happy path，而是明确覆盖 `+需求`、核心对象、状态逻辑 entity 分组、状态逻辑按 entity 分桶分步合并、折叠子卡/逐条转移摘要、人员组织或历史详情删除中的高风险分支。

- 已形成可直接执行的首批 fixture 覆盖矩阵和优先级顺序。

### 9.2 不算完成的情况

- fixture 只覆盖低风险 happy path。
- 高风险区没有被纳入首批覆盖。
- `task1` 仍只有旧版初步需求 fixture，未覆盖最新工作区扩展链路、状态逻辑 entity 分组/折叠或状态逻辑按 entity 分桶分步合并链路。
- 没有说明每个 fixture 为什么存在、验证什么。
- 历史侧栏没有单独的富场景 fixture，导致结构级接管无从验收。
- fixture 集合没有优先级，后续无法决定先跑什么。
