### 7.3 task1 初步需求链路拆责

| 关注点 | 主责任模块 | 辅助模块 | 固定结论 |
| --- | --- | --- | --- |

| 初步需求 V2 深度提炼 | `preliminaryRequirement.js` `parsePreliminaryRequirementDepthV2` | runtime | 提炼规则、schema 与 JSON 语义在 `preliminaryRequirement.js` |

| “对补充内容修改” | `main.js` `runTask1PreliminarySupplementModifyWithFeedback` | `preliminaryRequirement.js` `refinePreliminaryRequirementV2WithFeedback` | 修订动作由 host 发起，但 V2 修订语义仍由 task1 模块收口 |
| 刷新 / bundle 后 task1 数据恢复 | `main.js` `applyPreliminaryReqHydrationFromMessages`、`pushTask1PreliminaryLlmQueryFromCaseIfNeeded` | `preliminaryRequirement.js` `extractPreliminaryReqV2FromChatMessages`、runtime 跟进态判定 | refresh 恢复不能靠 Vue 私读内部状态，必须走现有 hydrate 链 |

### 7.4 最小链路结论

1. online 输入先经 `SmartCto.problemCaseApi.refreshProblemDetailBundle()` 进入 `main.js`。
2. `main.js` 把 bundle、持久化数据与聊天 hydrate 成 `SmartCto.appState` 当前快照。
3. runtime / chat 只通过 `app-state` 与 `__host` 消费当前快照，并在动作后推动 `renderProblemDetailContent()`、`renderProblemDetailChatFromStorage()`、`renderProblemDetailHistory()`。
4. renderer / history / events 只消费或转发，不反向定义语义。
5. 因此后续 host / selector / command 合同必须围绕 `app-state + runtime + preliminaryRequirement + main bridge` 设计，不能直接以 DOM 或 legacy 私有局部变量为数据源。
