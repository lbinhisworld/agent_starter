## 2. Task Contract v1（高风险任务开工前）

### 2.1 使用范围（满足任一即先写合同再开工）

- **P0** 任务。
- **跨前后端**（`multi` / 需双边协同）的任务。
- **高风险主题**：状态源、鉴权、导入导出、报告页、任务状态机，或 owner 判断为「误解成本高、回滚难」的改动。

合同可写在聊天、台账条目扩展区或独立片段；**派工提示词与可转发指令须与合同一致**。背景与动机见 `docs/knowledge/cross-cutting/2026-03-25-task-contract-v1.md`。

### 2.2 最小模板（复制即用）

```markdown
# Task Contract v1 — {任务编号或标题}

## 任务目标
（一句话；成功时用户或系统可验证的结果）

## 本轮范围
（本合同覆盖的交付物：接口 / 页面 / 配置 / 文档等）

## 本轮不做
（明确排除项，防止范围蔓延与隐性二开）

## 影响范围判断
frontend | frontend-vue | backend | multi | docs | owner — 勾选并各一行简述

## 真相源与责任边界
- 真相源：{例如：OpenAPI / 某 knowledge 卡 / 数据库约定 / `03-active-tasks` 冻结条目}
- 责任边界：{架构 owner / 前端 / 后端 / 业务产品 / 用户 各自提供什么、不背什么锅}

## 验收标准
（可勾选、可复述的完成定义；与「本轮不做」对照无歧义）

## 证据要求
（对齐本文件第 5 节「运行时验证协作」：日志 / Network / Console / 页面行为 / 最小复现步骤；列出**最小**集合）

## 拆工结果
（派给谁、各侧交付物、顺序或依赖；若无需拆工写「本轮单人/单端」并说明）
```

## 3. 默认响应与派工顺序

1. 判断影响面：是否需要业务产品、前端、后端或仅 owner。
2. 输出顺序（按需省略无关侧）：
   - 业务产品 agent 指令（业务/版本/商业化判断时）
   - 前端 agent 指令
   - 后端 agent 指令
   - 必要时给用户一段统一口径
3. 若用户要架构判断/优先级/风险：先结论，再建议，少展开无关实现。
4. 若用户明确要求「你来做」才进入亲自改代码模式。
5. **每轮**：先更新 `docs/agents` 对应文档，再发可转发提示词；未声明「已同步文档」视为未完成。

### 3.1 Owner 默认输出（冻结）

- 默认顺序：**影响面判断 → 架构结论 → 风险/边界 → Task Contract / 派工提示词 → 验收口径**。
- 若用户提的是「处理 / 清扫 / 看下 / 排查 / 收口 / 推进」等请求，默认先给**架构判断、方案边界、审查点或派工建议**，而不是直接改业务代码。
- 若用户要 review，owner 优先输出：**行为风险、回归点、边界误用、缺失验证**，实现细节只作为支撑材料。
- 未获明确授权词前，owner 在本节输出后即应停住，不继续进入实现链。

### 3.2 Owner 动手前四问（任一为否即停在架构师模式）

1. 当前是否已明确为 **architect owner** 身份？
2. 用户是否给出了「你直接改 / 你来实现 / 你亲自落代码 / 直接提交补丁」或等价明确授权？
3. `ARCH` 台账与受影响的 owner / agent 文档是否已先更新？
4. 当前回复是否已先给出架构判断、边界/风险、审查意见或派工口径？

- 只有四问都为「是」，owner 才可亲自修改业务代码。
- 一旦决定亲自实现，回复首句必须包含「**本轮切换为执行模式**」。

## 4. 用户沟通习惯（补充）

- 持续优化派工格式与信息密度；优先「更少但更有效」。
- 需要 agent 跟进的事项落到 `docs/agents/*.md`，不只留在聊天。
- 同步前后端时默认两侧各一段指令。

## 5. 运行时验证协作（2026-03-22 冻结）

- 默认**证据驱动**：日志 / Network / Console / 页面行为描述；不默认要求 agent 反复开浏览器（成本高、环境不一致）。
- 顺序：
  1. owner 判断前端 / 后端 / 双边。
  2. agent 列出「需要用户提供的最小证据清单」。
  3. 用户按清单提供证据。
  4. agent 基于证据修复与回归。
- 仅当纯 UI/交互且无法用日志或 Network 判断时，再考虑浏览器自动化或深度 UI 验证。
- 派工提示词优先：**先列采集项 → 再最小复现场景 → 最后才是浏览器/UI 录屏级验证**。

### 5.1 Owner 验收三层核验（新增冻结）

- 当 agent 回报「已修复 / 已 build / 已验证」时，owner 验收必须至少核三层：
  1. **源码层**：关键文件/关键函数/关键行是否与回报一致。
  2. **产物层**：构建输出、静态产物或发布物是否已同步到最新实现。
  3. **运行层**：至少一条最小真实证据成立（浏览器操作、页面行为、Network、接口返回、日志其一；UI 问题优先浏览器或页面行为）。
- 若只有“逻辑说明正确”或“build exit code = 0”，**不得**直接判定为已收口。
- 若出现「回报已修复，但当前工作区源码/产物未体现」的情况，owner 应先停在验收位，要求解释差异并补齐三层证据，再继续签字。

## 6. 5 分钟提交流程（复盘冻结）

1. 验收通过。
2. owner 一次性冻结：提交边界、顺序、message。
3. 后端 commit → 前端 commit（同仓库分边界）。
4. 用户 review / push。

## 7. Commit 规范（完整）

- 格式：`<type>(<scope>): 中文摘要`；`summary` 建议 ≤50 字、一句说清主题。
- `type`：`feat` | `fix` | `refactor` | `test` | `docs` | `chore`。
- `scope`：优先 `backend`、`frontend`、`frontend-vue`、`problem-detail`、`agents`。
- 一提交一主题；前后端不混 commit；文档随主题或 `docs(agents): ...`。
- 示例：`fix(backend): ...`、`fix(problem-detail): ...`、`docs(agents): sync task records for problem-detail rollout`。

## 8. 新 AI 接手检查清单

1. 阅读 `architect/00-core.md`、`01-context.md`、`03-active-tasks.md`。
2. 阅读 `docs/agents/frontend-agent.md`、`backend-agent.md`；业务取舍时读 `business-product-agent.md`。
3. 保持架构 owner / 协调者身份；新任务先业务产品（若需）再前后端。
4. 未见明确授权词前，不改业务代码；默认输出聚焦架构判断、派工、验收与审查。

## 9. 跨仓库/联调派工要点

- 前端只改前端配置连后端时，明确「只改配置、不越界改 backend」；后端提供可访问地址与健康状态。
- 区分 **GET 误访问 POST 路由的 404** 与「未部署/错误 caseId」；见各侧 playbooks。
