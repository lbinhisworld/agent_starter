# Smart CTO 后端整体架构设计

## 1. 设计目标

本架构设计基于当前业务现状，目标是把系统从“前端本地存储 + 前端直连模型”升级为“前后端分层 + 数据库统一存储 + 后端统一编排 AI 调用”的架构。

核心目标：

1. 后端成为唯一业务真相源
2. 所有核心数据持久化到数据库
3. 所有大模型调用统一收口到后端
4. 支撑 `Home -> ProblemDetail -> Tools` 三条主业务链路
5. 兼容当前 15 个任务节点的状态机与回退逻辑
6. 为后续多用户、权限、审计、日志、统计预留空间

## 2. 技术选型建议

推荐组合：

- 运行时：`Node.js`
- 后端框架：`NestJS`
- ORM：`Prisma`
- 数据库：`MySQL 8`
- 接口风格：`REST API`
- 鉴权：第一阶段可先不做，第二阶段补 `JWT + Session`
- 异步任务：第一阶段可同步执行，第二阶段可引入队列

推荐原因：

- `Node.js` 与当前前端 TypeScript 栈一致
- `NestJS` 更适合中大型业务模块化拆分
- `Prisma` 适合快速建模、迁移、类型推导
- `MySQL` 足够支撑当前“结构化主数据 + JSON 任务结果”的模式

## 3. 后端职责边界

后端需要承担的职责：

1. 问题案例主记录管理
2. 企业分析查询与持久化
3. 15 个任务节点状态机推进
4. 聊天消息管理
5. 结果卡生成、确认、修正、讨论
6. 回退、重置、重启当前任务
7. 沟通历史生成与查询（与 `frontend/数字化问题跟进阶段设计.md` §0.6、`frontend/对话模型管理.md` 中过程日志分段与标签规则及 **任务Skill** 时间线数据源对齐；侧滑面板样式见 `frontend/styles.css` 中 `.problem-detail-history-panel`）
8. 工具知识库主题与内容管理
9. 所有 AI 调用统一编排
10. 数据审计、操作日志、错误日志

前端保留的职责：

1. 页面展示
2. 轻量 UI 状态
3. 当前输入态
4. 折叠、切换、选中、滚动等交互状态

## 4. 整体架构分层

建议后端采用 5 层结构：

1. `Controller` 层
   - 接收 HTTP 请求
   - 参数校验
   - 响应格式统一
2. `Application / Service` 层
   - 业务编排
   - 事务控制
   - 状态推进
3. `Domain` 层
   - 任务状态机
   - 回退规则
   - 结果卡规则
4. `Repository` 层
   - Prisma 数据访问
5. `Infrastructure` 层
   - 大模型适配
   - 外部企业分析服务适配
   - 缓存、日志、配置、队列

## 6. 核心模块设计

### 6.1 problem-cases 模块

这是系统最核心的业务模块。

负责：

- 首页问题案例创建、查询、删除
- 问题详情主记录读取
- 主阶段状态维护
- 当前任务状态维护

核心子能力：

- `ProblemCaseService`
- `ProblemCaseQueryService`
- `ProblemCaseCommandService`
- `ProblemCaseRepository`

建议聚合根：

- `ProblemCase`

建议该聚合维护的状态：

- 基本客户信息
- 当前主阶段
- 当前策略子阶段
- 已完成任务集合
- 工作区最新结果快照

### 6.2 task-orchestration 模块

这是问题详情页业务编排中最重要的一层。

负责：

- 启动任务
- 推进任务
- 校验任务是否允许执行
- 任务完成后推进阶段
- 结果卡生成
- 结果卡确认
- 修正 / 讨论分支
- 回退 / 重置 / 重启当前任务

建议拆为：

- `TaskStateMachineService`
- `TaskExecutionService`
- `TaskRollbackService`
- `TaskResultService`

这一层应沉淀：

- 15 个任务节点定义
- 每个任务的前置条件
- 每个任务的输入上下文构建规则
- 每个任务的输出落库规则

### 6.3 ai 模块

负责统一管理模型调用，不允许业务模块直接访问模型 SDK 或 HTTP。

建议拆分：

- `AiGatewayService`
  - 统一模型调用入口
- `PromptTemplateService`
  - 管理 prompt 模板
- `AiTraceService`
  - 记录请求、响应、耗时、用量
- `DeepSeekAdapter`
  - 当前模型提供商适配器

建议职责：

- 提供通用 chat 能力
- 提供任务型生成能力
- 提供工具知识库分析能力
- 统一限流、超时、重试、fallback

### 6.4 company-analyses 模块

负责企业分析链路。

包括：

- 企业分析查询
- 企业价值流查询
- 企业分析记录保存
- 企业分析详情获取

如果后续仍需调用外部企业分析服务，建议由后端代理：

- `ExternalCompanyAnalysisAdapter`
- `ExternalValueStreamAdapter`

不要让前端继续直连第三方分析接口。

### 6.5 tool-knowledge 模块

负责工具知识库。

包括：

- 主题管理
- 知识条目管理
- 工具对话
- 意图识别
- 自动沉淀

建议拆分：

- `ToolTopicService`
- `ToolEntryService`
- `ToolDiscussionService`

其中：

- 意图识别走 AI 模块
- 知识沉淀走 AI 模块
- 最终落库走 tool-knowledge 模块

### 6.6 operation-history 模块

负责记录关键可回滚操作。

包括：

- 任务回退前快照
- 删除消息前快照
- 重启当前任务前快照
- 重置前快照

这是保证“旧系统回退能力”能够在后端稳定实现的关键模块。

## 7. 核心业务流设计

### 7.1 首页创建问题案例

流程：

1. 前端提交原始客户问题文本
2. 后端调用 AI 做结构化解析
3. 返回解析预览
4. 前端确认创建
5. 后端写入 `problem_cases`
6. 返回新案例记录

涉及模块：

- `problem-cases`
- `ai`

### 7.2 ProblemDetail 任务推进

流程：

1. 前端点击“确认开始”
2. 后端校验任务是否可启动
3. 写入任务开始消息
4. 如需用户补充信息，则返回等待输入状态
5. 用户提交内容后，后端构建任务上下文
6. 调用 AI 生成结果
7. 落库存消息与结果卡
8. 前端点击确认结果卡
9. 后端更新任务状态
10. 若满足推进条件，更新主阶段
11. 自动生成下一任务启动通知

涉及模块：

- `problem-cases`
- `task-orchestration`
- `ai`
- `operation-history`

### 7.3 修正 / 讨论分支

流程：

1. 前端对结果卡发起“修正”或“讨论”
2. 后端记录反馈消息
3. 构建当前任务结果 + 用户反馈上下文
4. 调用 AI 生成修正结果或讨论回复
5. 生成新的消息或新的结果卡版本
6. 写入消息表与任务状态表

### 7.4 回退任务

流程：

1. 前端请求回退到指定任务
2. 后端校验是否可回退
3. 生成回退前快照
4. 清理目标任务之后的结果、消息、任务状态
5. 重建主阶段和当前任务状态
6. 返回最新详情

注意：

回退不是简单字段修改，必须作为事务操作。

### 7.5 工具知识库沉淀

流程：

1. 前端发送工具讨论内容
2. 后端调用 AI 判断意图
3. 根据意图执行：
   - 新增主题
   - 补充知识
   - 普通讨论
   - 修改知识
   - 删除知识
4. 返回最新主题状态和聊天消息

## 8. 数据库建模策略

建议采用“关系字段 + JSON 快照”混合建模。

### 8.1 适合强结构化建模的数据

- 案例主记录
- 任务状态
- 主题列表
- 消息基础字段
- 用户、组织、权限

### 8.2 适合 JSON 建模的数据

- `basicInfo`
- `bmc`
- `requirementLogic`
- `valueStream`
- `globalItGapAnalysis`
- `localItGapSessions`
- `rolePermissionSessions`
- 回退快照
- 消息 payload

原因：

这些字段结构会随业务迭代频繁调整，不适合过早拆成大量细表。

## 10. 事务边界设计

以下动作必须用事务：

1. 确认结果卡并推进任务
2. 回退任务
3. 删除消息并回滚状态
4. 重置案例
5. 重启当前任务

原因：

这些动作至少同时影响：

- 主记录
- 任务状态
- 消息记录
- 历史快照

如果不做事务，数据很容易不一致。

## 11. AI 编排层设计

建议后端不要让每个业务模块自己拼 prompt，而是统一通过 AI 编排层输出。

推荐模式：

### 11.1 Prompt 模板中心

按业务维护 prompt：

- 首页问题解析
- task1 企业背景洞察
- task2 商业模式画布
- task3 需求逻辑构建
- task4 价值流（前端：Mirror + 按 VSM 阶段分步架构加固；`VALUE_STREAM_PROMPT_MIRROR` / `VALUE_STREAM_PROMPT_STAGE_HARDENING`）
- task5-task15 后续任务
- 工具知识库意图识别
- 工具知识摘要
- Ask 模式问答

### 11.2 上下文构建器

每个任务单独提供 context builder：

- `buildTask1Context`
- `buildTask2Context`
- `buildTask3Context`
- ...

### 11.3 AI Trace

建议落库：

- `requestId`
- `caseId`
- `taskId`
- `promptName`
- `model`
- `latencyMs`
- `tokenUsage`
- `status`
- `errorMessage`

## 12. API 设计原则

建议遵循以下原则：

1. 前端不直接拼业务状态
2. 前端拿到的详情接口应尽量接近页面所需结构
3. 结果卡确认、修正、讨论要使用明确命令式接口
4. 回退、重置、重启当前任务不使用普通 update 接口，而使用动作型接口

建议风格：

- `GET /api/problem-cases/:id`
- `POST /api/problem-cases/:id/tasks/:taskId/start`
- `POST /api/problem-cases/:id/tasks/:taskId/confirm`
- `POST /api/problem-cases/:id/tasks/:taskId/revise`
- `POST /api/problem-cases/:id/tasks/:taskId/discuss`
- `POST /api/problem-cases/:id/tasks/:taskId/rollback`

## 13. 权限与安全

第一阶段如果只是内部使用，可以先弱化。

但架构上建议提前预留：

- 用户表
- 组织表
- 案例归属字段
- 创建人、更新人
- 操作日志

安全上必须注意：

1. 模型 API Key 只保存在后端
2. MySQL 不暴露公网
3. 所有写操作记录操作人和时间
4. 输入内容做长度限制和校验
5. AI 响应做兜底解析，不能直接信任模型输出

## 14. 性能与扩展建议

第一阶段可以全部同步处理。

第二阶段建议扩展：

1. 将耗时 AI 任务改成异步任务
2. 增加任务队列
3. 为 `GET detail` 做缓存
4. 为知识库和历史查询增加分页

可扩展点：

- Redis
- 消息队列
- 对象存储
- 向量检索

但第一阶段都不是必须。

## 15. 推荐落地顺序

### 第一步：搭后端骨架

先完成：

- NestJS 工程初始化
- Prisma 初始化
- MySQL 连接
- 健康检查接口

### 第二步：先打通首页链路

- 问题解析
- 创建案例
- 列表查询
- 删除案例

### 第三步：打通 ProblemDetail 主记录

- 获取案例详情
- 获取消息
- 获取任务状态

### 第四步：打通任务推进主链路

- 启动任务
- 发送用户输入
- 生成结果卡
- 确认结果卡

### 第五步：补回退、重启、重置

这部分复杂度最高，建议在主链路稳定后做。

### 第六步：接 Tools 页

- 主题列表
- 条目管理
- 工具聊天

## 16. 结论

对于 Smart CTO 当前业务，后端不是一个简单的 CRUD 服务，而是一个“业务状态机 + AI 编排服务 + 数据中心”。

因此最适合的架构不是把所有逻辑堆在 Controller，而是：

- `problem-cases` 管主记录
- `task-orchestration` 管状态机
- `ai` 管模型编排
- `operation-history` 管回退快照
- `tool-knowledge` 管知识沉淀
- `company-analyses` 管企业分析

建议以后端作为唯一状态源推进，前端只做展示和交互，逐步替换当前本地存储与前端编排逻辑。
