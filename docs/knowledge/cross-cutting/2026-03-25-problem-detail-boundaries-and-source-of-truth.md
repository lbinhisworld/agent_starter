# ProblemDetail：前后端职责边界与真相源（收口路径）

## 元数据

- 适用模块：`multi`（`frontend` / `frontend-vue` / `backend` 协作）
- 关联任务：`ARCH-20260325-03`（cross-cutting 知识卡迁移 · 第一批）
- 状态：active

---

## 适用范围

- 案例详情页（`ProblemDetail`）、首页列表、聊天时间线、导入导出案例包、售前报告/工作区等多视图**同时存在**时的状态一致性问题。
- **online**（走后端 API）与 **local**（`localStorage` 等）两种运行形态并存时的「谁说了算」争议。
- 症状包括：刷新后详情丢失、深链打不开、列表与详情不一致、任务推进与消息时间线错位、多 Tab/多入口看到不同案例状态。

---

## 问题模式

| 模式 | 典型表现 | 根因方向（优先怀疑） |
| ---- | -------- | -------------------- |
| 路由键错误 | URL 无 `caseId`、分享/刷新无法恢复 | 前端仍用 `sessionStorage` + `createdAt` 当主键，未与后端 `ProblemCase.id` 对齐 |
| 多源各写各的 | 列表已更新、详情仍是旧数据；或反之 | 列表缓存、详情请求、聊天块本地拼装未指向**同一案例标识** |
| 整段覆盖消息 | 误删历史、PUT 体过大、400/500 | 仍走兼容路径「全量 `PUT /messages`」而非追加/单条 PATCH |
| 环境漂移 | 本地代码「已修」但现场仍旧行为 | 未做运行时四件套（见同目录 `2026-03-25-runtime-verification-four-checks.md`） |
| 假完成 | 工作区已有分析卡，但无法进入下一任务 | **任务状态机**以 `completedTaskIds` 与确认块为准，不以「是否生成过卡片」为准（专项见后续任务状态机知识卡） |

## 真相源分层

### 1. 运行形态：online 与 local 是两套真相，不要混用规则

- **online**：持久化与规则裁决以 **后端** 为准：`GET /api/problem-cases/:caseId`、`messages`、`tasks`、任务动作接口。AI 配置等读 **数据库/AppSetting**，不读前端 `config.local.js` 里的 key。
- **local**：以 **浏览器本地存储** 为真相；不与 online 自动同步。讨论缺陷时必须先明确当前是 online 还是 local。

### 2. 业务数据：后端案例主键与字段分工

- **对外唯一案例标识**：`ProblemCase.id`（后端生成的 `caseId`，如 `problem_…`）。列表、详情、消息、任务、导入导出、报告聚合接口均应围绕该 id 对齐。
- **`createdAt`**：时间戳/展示与兼容用；**不得**再作为详情页路由主键或跨刷新定位的主标识。
- **前端传入的临时 id**（如时间戳）：创建时可能被后端忽略，**以后端响应中的 `id` 为准**接续后续请求。

### 3. 视图层：detail / list / chat / bundle 为何容易「各有一份状态」

- **列表**：往往来自缓存或一次 list 请求；导入/创建后若未刷新列表，会与详情脱节。
- **详情**：一次 `GET :caseId` 或聚合数据；若路由上案例 id 与内存中当前 item 不一致，会读到「别的案例」。
- **聊天块**：历史上常由前端拼装并回写；它只是 **呈现层**，不是持久化的唯一来源。
- **案例包（export/import）**：是快照；导入会 **新建** `caseId`/`messageId`，不能与「就地覆盖当前页内存」混为一谈。

### 4. 消息时间线：唯一权威来源应是后端模型

- 目标口径：**`ProblemCaseMessage`（经 `GET .../messages` 等）为唯一消息时间线来源**；新增应为 **追加**（`POST`），避免默认走整段 `PUT` 覆盖。
- 兼容 `PUT /messages` 仍可能存在：仅作过渡；大时间线全量回写会带来体积、校验与覆盖风险。

### 5. 报告页 / 工作区 / 详情态应共用「当前案例」真相

- **当前打开的案例**应由统一状态表示：**URL 查询参数中的 `caseId` + 与之一致的内存中的当前 case 对象**（以及 online 下后端返回的 detail）。
- 报告聚合（如 `GET .../report`）、工作区任务卡、详情首屏应读取 **同一 `caseId`** 下的数据；若某块仍从旧缓存或仅聊天块推导，会出现「报告有、详情无」或任务阶段不一致。

### 6. 为什么「聊天块不是唯一真相源」

- 聊天 UI 可能合并了占位符、本地未同步草稿、历史兼容结构；**持久化与任务是否完成**必须由后端消息与任务状态 + 前端 `completedTaskIds` 等**约定字段**共同判定，不能只看气泡是否出现。
- 若「以聊天为准」去覆盖写回，容易触发整段 PUT、与 `GET` 返回的 nullable 字段不对称等问题。

## 常见误区

1. **用 `createdAt` 当主键**做 storage key 或路由 → 与后端 `caseId` 分叉，深链与跨设备不可用。
2. **把「接口返回 200」当成「用户浏览器已跑在新代码上」** → Node 无热重载，旧进程路由表可能仍是旧 dist（见运行时四件套）。
3. **浏览器地址栏直接 GET 一个 POST 路由** → 404，与「未部署」混淆；应看 Network 里真实方法与鉴权。
4. **把「工作区里已有分析结果」当成任务已完成** → 未完成确认块、`completedTaskIds` 未写入则状态机仍停在当前任务。
5. **online 下调试 AI 却只改前端配置** → key 在后端库表；前后端各查各的会误判「本地明明配了」。

---

## 判断顺序（建议）

1. **先定运行形态**：online 还是 local？配置里 `BACKEND_API_URL` 指向哪里？
2. **再定当前案例 id**：URL、Network 请求路径、后端响应里的 `id` 是否**同一 `caseId`**？
3. **再定数据从哪来**：详情是 `GET :caseId` 还是旧列表项；消息是 `GET .../messages` 还是纯前端数组。
4. **再定是路由/缓存/契约哪一类**：刷新丢状态 → 优先路由与主键；列表不刷新 → 前端缓存刷新链路；400/413 → 对照契约与 payload。
5. **最后才扩 scope**：避免同时改前后端；先最小证据再改代码。

## 修复优先级（一般原则）

| 优先级 | 归责倾向 | 说明 |
| ------ | -------- | ---- |
| P0 | 后端 | 主键生成、消息/任务持久化、鉴权、接口语义与错误码、空更新/404 误判等 **HTTP 与数据模型** |
| P0 | 前端 | URL 携带 `caseId`、history 与深链、`createdAt` 降级为展示、列表与详情共用当前 case、减少整段 PUT、import 后刷新列表 |
| 需对齐 | 双方 | `GET`/`PUT` 字段 nullable 对称、import 的 `Content-Type`、任务完成与消息追加的调用顺序 |

**不要**在未确认运行实例与 `caseId` 一致时，仅凭前端静态路径推断「已修复」。

## 前端详情页：同会话内多案例切换（补充，2026-04-03）

- **与「后端 caseId 真相源」正交**：即使 URL 与 `currentProblemDetailItem` 已指向案例 B，若内存中 `problemDetailChatMessages` 仍保留案例 A 的数组且被 canonical 逻辑误用，仍会出现「B 的阶段条像 A」的串案表现。
- **收口**：通过 `problemDetailChatMessagesCaseKey` 与 `getProblemDetailChatMessagesForCanonical` 的键一致门控、换案与 bundle 刷新时的键失效，保证推导 pipeline 使用的 messages 与当前案例一致。详见 `docs/design/problem-detail-multi-case-and-task1-json.md`。
