# 任务级修改、Skills 沉淀与沟通历史 skill 呈现

## 元数据

- 适用模块：multi（产品目标 + 交互语义 + 数据沉淀原则 + UI 结构）
- 关联任务：`BP-20260323-03`、`BP-20260323-04`、`BP-20260323-05`、`BP-20260325-07`；工程实现以各 FE/BE 台账为准
- 状态：active（正文主源；旧 `business-product-agent.md` §14.5、§14.6、§14.8 已收敛至此）
- **姊妹篇**：task11 建模与「按新提示词重推演」专项见 `2026-03-25-task11-core-business-object-boundary.md`

## 产品目标

1. **产出后仍可演进**：承认真实项目中「一次生成即交付」不成立，必须在主链路内支持**针对某一任务成果的定向修改**，而非每次都从头跑全链路。  
2. **修改过程可学习**：把「为何改、改成什么、策略是什么」结构化沉淀为**可检索、可回放**的经验，反哺同类任务与提示词治理。  
3. **提示词可见、可对比**：提示词是质量杠杆；用户需要独立於「执行过程日志」之外，看到**提示词版本如何随时间变化**，并能对照结果变化。  
4. **入口分层**：全局有一个「按任务聚合的 Skills 库」；在沟通历史的**单任务上下文**内，又能就地查看该任务的 skill 时间线，减少跳转成本。

---

## 为什么要做「任务级修改」

- **问题不在模型而在业务**：首次产出往往缺客户侧约束，修订是常态；若不提供任务级入口，用户只能用泛聊或重跑链路，**成本高且不可审计**。  
- **修订本身是资产**：动因、范围、策略若散落聊天，无法复用；绑定到任务、沉淀为 skills，才能把个案变成**组织可继承的约束**。  
- **与过程日志分工**：过程日志回答「这一步执行发生了什么」；任务级修改强调**对既有成果的受控改写**，并产生**意图确认**这一可审计环节。

## 交互序列（逻辑层）

下列描述**产品语义顺序**；具体控件命名以实现为准。

### 进入与选择

1. 用户在聊天侧进入**任务级修改**意图（含从任务完工区发起「请修改」等入口）。  
2. 系统列出**可选任务**；不可选任务必须展示**原因**（未开始、尚无成果等），避免误判。  
3. 选定任务后，界面进入**修改态**（视觉与文案上与常规模式区分），并下发统一引导：明确针对**该任务已有成果**征求修改意见。

### 意图提炼与确认（核心）

4. 用户用自然语言描述修改诉求后，系统先做**修改意图提炼**（结构化），至少包含：  
   - **修改动因**：为何改（客户反馈、事实纠偏、约束变化等）  
   - **修改目标**：期望把结果调整到什么方向/范围  
5. 在聊天区呈现**确认卡片**，由用户确认后再进入正式改写；避免模型直接「猜着改」。  
6. 在任务时间线上沉淀**可回放**的「修改提炼」类过程信息（与最终成果区分：**前者是证据链，后者是交付物**）。

### 新提示词与再生成（与通用 / task11 分叉）

7. 确认意图后，进入**提示词修订**与「是否按新提示词再生成」的确认流。  
8. **通用任务**：在确认新提示词后，可按产品约定走**再调用模型**产出更新后的业务结果（实现上常见为两阶段 LLM + 确认）。  
9. **task11**：因入参形态与「清空工作区 / session 重发」语义特殊，**不**沿用通用第二轮 Chat；**产品冻结语义**见 `2026-03-25-task11-core-business-object-boundary.md` 专项节——本文不重复展开。

### 写回与沉淀

10. 用户确认接受修改结果后，写回对应任务成果，并把本次可复用信息写入**任务级 skills 备注**（或等价结构化存储），与任务强绑定。

## 可选任务规则（首版口径）

| 状态 | 是否可选（首版） | 说明 |
| ---- | ---------------- | ---- |
| 尚未开始 | 否 | 无修改靶标 |
| 已产出成果（含客户未确认） | 是 | 修改针对已有成果 |
| 尚无成果 | 否 | 禁用原因对用户可见 |

## 数据沉淀原则（Skills / 学习能力）

每次任务级修改，宜至少能回答四类问题（用于检索与复盘，而非散文）：

1. **触发**：为何改（客户/事实/约束）  
2. **对象**：哪个任务、哪些关键字段或段落  
3. **策略**：新增 / 删除 / 重写 / 合并  
4. **影响**：对下游任务或交付物的影响

沉淀位置应支持：**按任务检索**、**时间顺序回放**、**与提示词版本关联**（见下两节）。

## Skills 作为「提示词知识库」：首页任务数据库

**定位**：在首页提供一级入口，进入**按 task1–task15 分栏**的「任务 skills 数据库」页面——同一任务下，以**时间线**组织每一次「有效沉淀事件」（如提示词更新、修改意图确认后入库等）。

**UI 结构原则**：

- **导航**：返回首页、页面标题、**15 个任务 tab** 快速切换。  
- **时间线节点（折叠态）**：至少可见 **时间戳** 与 **档案标识**，支持从最近优化往回追。  
- **展开态**：展示该时刻的**系统设计/提示词**正文或可检索摘要，并标注**版本语义**（如 V3.3）与**变更来源**（自动生成、人工修订、修改模式沉淀等）。  
- **空态**：某任务尚无沉淀时，明确提示「暂无记录」，避免与加载失败混淆。  
- **排序**：默认**最新在上**，便于关注最近一次变更。

## 沟通历史内的 skill tab：就地查看版本演进

**产品价值**：用户常在单任务沟通上下文中排障；若必须跳到其他页面才能看提示词历史，**「提示词变更 → 结果变化」** 的因果链断裂。

**与过程日志的边界**：

- **过程日志**：执行过程事件（调用、分支、报错等）。  
- **skill tab**：**提示词版本事件**——二者并列、互不替代，支持对照回放。

**UI 表达原则**：

1. **三 tab 并列**：任务详情、过程日志、**skill**（同一任务节点内）。  
2. **当前最新置顶**：列表顶部固定 **「当前最新版本 Skill」** 快照卡，正文与**当前生效**提示词一致；避免用户滚到底才知「现在用的是哪版」。  
3. **历史节点**：时间线节点按时间**升序**展开（早在上、晚在下）；**最新**由顶部快照承担，而非与历史列表抢「排序语义」。  
4. **节点展开**：建议用**双子信息结构**——「相对上一版的差异摘要」与「本版完整 Skill」对照，降低对比成本（色彩体系统一即可，具体色值以实现为准）。  
5. **初始化**：任务创建时即写入**首个 skill 节点**（时间对齐任务创建时刻，内容对齐当时系统提示词）；后续每次提示词变更**追加节点**，**不覆盖**历史。

**使用边界**：skill tab **不**承担业务 JSON 的执行调试职责；执行细节仍在过程日志与任务详情。

## MVP 验收口径（汇总）

**任务级修改**

- 可选任务规则生效，禁用原因可见。  
- 修改态视觉/文案可识别；引导语准确指向「对该任务成果」修改。  
- 用户描述后能产出**意图确认**（至少含修改动因与修改目标），确认后才改写。  
- 时间线上可区分「修改提炼」与「修改后成果」。  
- 修改可关联到任务级 skills 沉淀。

**首页 Skills 数据库**

- 可从首页进入；标题区含返回、标题、task1–15 tab。  
- 各 tab 可渲染时间线；节点具备时间戳与档案级标识；可展开查看提示词/设计内容。

**沟通历史 skill tab**

- 每任务节点可见 skill tab；顶部有当前最新快照；新建任务即有首节点；后续更新追加不丢历史。
