## 为什么 task11 是关键环节

- **结构枢纽**：对象是否存在、如何承接存量、状态如何跃迁，直接约束后续字段设计、状态机与关系映射；此处摇摆会导致下游反复返工。  
- **输入天然「厚」**：需同时消化 **价值流压缩 JSON、ITGap 压缩 JSON、角色权限推演 JSON** 三类上下文，信息密度高。  
- **输出天然「大」**：既要给出**对象层**结论（新增/承接/类型），又要给出**可辩护的设计理由**与**状态语义**；若再混写字段层，单次响应极易失控。

因此 task11 不是「多生成一点 JSON」，而是主链路上**承上启下的结构化关口**。

---

## 对象爆炸、上下文失真与「两步法」

### 对象爆炸从何而来

若采用「滚动累加式对象池」或缺少硬控量，模型会为凑闭环不断造表，对象池随环节增长，**上下文体积持续膨胀**——这不是单纯的「写多了」，而是**不可控的建模发散**，反过来拖垮稳定性。

### 上下文失真表现

在「输入厚 + 输出也要厚」时，单次生成常见失败模式包括：**截断**、**字段缺失**、**JSON 结构漂移**、**阶段间语义不一致**。根因不是「模型不够强」，而是**把骨架决策与字段展开绑在同一次生成里**，提示词负载与输出空间同时爆炸。

### 两步法的职责划分（主干）

| 层级 | 回答的问题 | 产出形态（概念上） |
| ---- | ---------- | ------------------ |
| **第一步：对象骨架** | 对象是否成立、类型与角色、是否承接存量、状态跃迁与溯源锚点 | 收敛边界、控量、可解析的「对象层」决策 |
| **第二步：字段设计** | 在对象边界已定的前提下，逐对象展开字段、类型、校验与必要嵌套 | 字段层细节，可逐对象、分阶段验收与回放 |

**预期收益**：降低单次提示词与输出负担，提高 JSON **可解析性与可回放性**，减少重试；让「先判边界、再填细节」与人工评审习惯一致。

## 从 V2 到 V3：设计递进（非版本流水账）

以下按**解决的问题类型**归纳；不必按时间背诵版本号，但要理解**为何 V3.3 成为当前冻结**。

- **V2 类思路（滚动对象池）**：强调环节内 CRUD 演进与防护字段，但**对象池随环节滚雪球**，上下文与可控性变差——这是被 V3 主干**替代**的方向。  
- **V3.0 骨架化**：从「滚动池」切到**骨架建模**，强调物理穿透、对象分类与**硬控量（最多 3 个）**、角色权责定界——先把每步输出范围压住。  
- **V3.1 价值驱动**：**如无必要，勿增实体**；对象数约束落到 **0–3** 且允许诚实输出 **0**；倾向**深度嵌套**而非碎片化多表——抑制为凑数造表。  
- **V3.2 承接与瘦身**：**存量承接**与「新建对象」分离表达（含对象 ID）；嵌套子表以**对象数组**等结构表达——让「本环节无新对象但有关键动作」可被严格说出。  
- **V3.3 闭环与冷启动（当前第一步冻结）**：强调在价值流入口**补齐业务物理底座**（如客户/供应商/员工等）；对象类型语义区分为 **基础产出 / 业务主产出 / 过程记录**——减少早期漏建、后期补洞的被动架构债。

---

## 主对象、存量承接与子表/模块：判断要点

下列可视为**长期有效的产品—建模判断**，用于区分「主对象」「承接动作」「子结构」而非死记模板：

1. **控量优先于堆表**：默认 **0–3 个对象**；若当前环节确实无独立对象，应允许 **0**，不要为了「看起来充实」造表（对象爆炸的根因之一）。  
2. **存量承接与新建分流**：若领域已有锚定对象，优先说清**承接关系**与身份，而不是再发明一个同名新概念。  
3. **类型语义（V3.3）**：区分**基础产出**、**业务主产出**、**过程记录**——避免把流水账过程误升格为「主实体」。  
4. **嵌套 vs 碎片化**：明细、子结构优先以**对象数组/嵌套模块**落在已选对象之下，避免拆成大量平级碎表。  
5. **冷启动**：在价值流入口即判断**物理底座**是否缺失；缺则先补底座，再谈环节内增量——否则后续环节会反复「补洞」。

## 当前冻结口径（第一步：V3.3）

- **冻结对象**：第一步（对象骨架层）提示词 **V3.3 架构闭环与冷启动版**。  
- **主干不得回退**：**0–3 控量**、**存量承接**、**冷启动初始化** 所构成的闭环逻辑，升级时只能在其上**增量约束**，不得弱化。  
- **升级记录义务**：若演进至 V3.4+，须同步说明：**动因**、**输入变化**、**输出结构变化**、**解析与兼容策略**（避免「silent upgrade」）。

## 与任务级修改的协同：task11「按新提示词重新推演」（专项）

> 通用任务的「修改 → 新提示词确认」在第二次确认后，会再走一轮 **Chat 式**调用，用「新 system + 用户侧上下文」一次性产出业务 JSON。  
> **task11** 的单环节调用形态是固定的 **user 模板 + 可替换 system**（价值流/ITGap/角色权限等走 user 段）。若强行走同一套通用第二轮，易与真实 task11 入参不一致，且**无法**在语义上清空「已推演环节」与工作区状态。

**冻结的产品行为（摘要）**：

1. 与通用任务共享前置：**请修改** → 用户描述 → **修改意图确认** → 首轮提示词修订（过程上可追溯）。  
2. 聊天区出现「新提示词确认」块后，用户**第一次点确认（task11）**：将确认后的 **system 全文**写入案例级 **`coreBusinessObjectSystemPromptOverride`**（持久化）；**不**触发通用第二轮 `modificationRegenerate` 类 Chat。  
3. 聊天区追加**二次确认通知**（文案约定为将按新提示词重新进行【核心业务对象推演】，需用户再次确认）。  
4. 用户**第二次点确认**：从完工集合中移除 task11（若曾标记完工）；**重新生成**与价值流对齐的 **sessions**，清空各环节已推演 JSON；**不再**重复刷屏类过程块，仅推送 **session 计划块**，由用户按既有习惯自动或逐项推演。  
5. 之后每一推演环节：若存在非空 **`coreBusinessObjectSystemPromptOverride`**，则 **整段替换**默认 V3.3 system；user 拼接规则不变。

**对照（理解用）**：

| 维度 | 通用任务（如 task1 / task4） | task11 |
| ---- | ----------------------------- | ------ |
| 第一次确认「新提示词」后 | 通常进入第二轮 Chat 并产出业务结果 | 写入 override + 要求第二次确认 |
| 过程日志中「按新提示词重生成」块 | 有（通用链路） | **无**（不走该 Chat） |
| 工作区 | 各任务自有逻辑 | 第二次确认后清空推演 JSON，重发 session 计划 |

**验收要点（产品）**：task11 路径下，第一次看到「将按新提示词重新生成」并确认后，**必须**再出现「将按新提示词重新进行【核心业务对象推演】…」类通知，且**第二次确认**后才清空 session 并重发计划；之后工作区回到待推演，后续环节使用用户确认的 system（直至 override 被清空或工程侧定义的回滚发生）。

更细的交互块命名与工程语义以实现与前端台账为准；**产品冻结语义**以本节为准。
