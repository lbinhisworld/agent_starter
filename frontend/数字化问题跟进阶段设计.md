### 0.2 顺序触发与当前任务追踪

- **顺序触发**：状态①结束后，当前任务切换到状态②；状态②结束后，当前任务切换到状态③；依次类推。
- **当前任务**：系统对每个问题单维护一个「当前任务状态」，表示当前应执行或正在执行的任务。当前任务 = 下一个待完成的状态（第一个未完成的 task 即为当前任务）。
- **状态推进**：任一任务完成（满足评价标准并用户确认）后，当前任务自动指向下一个未完成任务；若所有 15 个任务均已完成，则当前任务为「已全部完成」。

### 0.3 任务扩展字段（在原有任务字段基础上）

每个任务（或每个问题单下针对每个任务的状态记录）增加如下字段：

| 字段 | 说明 |
|------|------|

| **动作** | 该任务的核心动作描述（如：提炼企业信息、生成 BMC、绘制价值流、标注 IT 现状等） |

### 0.5 与既有存储的映射

- **currentTaskIndex / currentTaskId**：可由既有 `completedStages`、`workflowAlignCompletedStages`、`itGapCompletedStages`、`currentMajorStage` 等推导出「当前任务」为 task1–task15 中的哪一个。

### 0.8 多案例切换时的详情页内存态（FE-20260403）

- **目标**：用户在首页/列表从案例 A 进入案例 B 时，**浏览大阶段**（`problemDetailViewingMajorStage`）、**工作区当前 task**（`getWorkspaceViewingTaskId`）、**canonical 推导**（`getCanonicalCurrentProblemFollowTaskState`）须仅依赖 **B** 的持久化案例数据与 **B** 的聊天记录，不得误用 A 留在内存中的聊天数组或子步骤索引。
- **聊天数组绑定**：`problemDetailChatMessages` 与 `problemDetailChatMessagesCaseKey`（同 `getProblemDetailChatStorageKey`）成对维护；`problem-detail-chat.js` 在 push 时写入键；换案、`bundle` 刷新重算 canonical 前将键置空，强制走持久化直至 `initProblemDetailChat` 再次加载。
- **等待修改态**：`problemDetailWaitingForFeedback` 在 `openProblemDetail` 时若 `createdAt`（存储键语义）与当前案例不一致则清空，避免 A 的 task4 修改等待显示在 B 上。

- **实现索引**：`frontend/js/core/app-state.js`、`frontend/js/api.js`（无）；`frontend/main.js`（`openProblemDetail`、`refreshProblemDetailBundleFromBackend`、`getProblemDetailChatMessagesForCanonical`、`initProblemDetailChat`）、`frontend/js/core/problem-detail-chat.js`。

### 0.7 任务完工确认块（`taskCompletionConfirmBlock`，全任务统一）

## 5. 聊天区的任务提示交互设计

### 5.1 设计原则

- **前置条件驱动**：仅当满足前置任务完成条件时，才展示下一任务的「即将开始」提示块。
- **用户确认**：每个「即将开始」类提示均需用户点击「确认」后才真正发起大模型调用。
- **状态反馈**：确认后按钮变为「已确认」并禁用，避免重复触发。
- **任务完工确认优先**：当出现任务完工确认块（「【任务名】是否视为完成？」）时，**下一任务的开始通知**仅当用户点击「已完成」后才弹出；不得在用户尚未点击「已完成」时提前展示下一任务通知。

### 5.2 需求理解阶段提示块

| 提示内容 | 前置条件 | 确认后动作 |
|----------|----------|------------|
| 任务通知：我即将开始【企业背景洞察】任务 | 当前第一个未完成任务为 task1，且聊天中尚无该任务启动通知 | 仅在聊天区推送系统消息「请提供企业基本工商信息」，**不**发送任务上下文内容卡片（taskContextBlock）；刷新工作区与标题栏。若来源于首页「启动跟进」，可在 task1 过程日志先写入一条 `LLM-查询`（备注：初步需求提炼），其输入/输出与 token/耗时复用首页「解析」调用数据。 |

### 5.3 页面刷新时的自动提示块策略（统一逻辑）

无论是首次进入问题详情还是刷新页面，只要打开问题详情页，系统会根据当前问题记录自动判断「下一个要开始的任务」，并自动尝试发起对应任务的提示块。整体策略如下：

- 初始化问题详情聊天区时（`initProblemDetailChat`）：
  - 总是尝试依次调用：
    - `maybeShowBmcStartBlock()`（Task2：商业画布加载）
    - `maybeShowRequirementLogicStartBlock()`（Task3：需求逻辑构建）
    - `maybeShowValueStreamStartBlock()`（Task4：绘制价值流）
    - `maybeShowItStatusStartBlock()`（Task5：IT 现状标注）
    - `maybeShowPainPointStartBlock()`（Task6：痛点标注）
    - `maybeShowItGapStartBlock()`（若有，为 ITGap 阶段做兜底）
  - 若当前大阶段已到达 ITGap 分析（`currentMajorStage >= 2`），则额外通过 `requestAnimationFrame` 调用：
    - `maybeShowE2eFlowExtractBlock()`（Task7：端到端事务流构建）
    - `maybeShowGlobalItGapStartBlock()`（Task8：**IT设计补齐**）
    - `forceShowLocalItGapStartBlock()`（Task9：角色汇总设计）
- 渲染 IT 策略规划工作区时（`renderProblemDetailContent` 且 `problemDetailViewingMajorStage === 3`）：
  - 始终渲染顶部任务按钮栏（Task10–Task15），并根据 `itStrategyPlanViewingSubstep` 决定当前选中任务；
  - 当当前子任务为 Task10（角色与权限模型推演）时，通过 `requestAnimationFrame` 调用 `maybeShowRolePermissionStartBlock()`：
    - 若尚未出现 `rolePermissionStartBlock` 且 `currentMajorStage === 3`，则在聊天区自动展示「即将开始角色与权限模型推演」提示块。

> **注意**：每个 `maybeShowXXXStartBlock` 内部都会检查前置条件（如：前一任务是否已完成、必要输入是否就绪、是否已经存在同类 startBlock、当前大阶段是否已超前等），因此多次刷新或重复调用不会导致重复提示。

**刷新后子步骤与滚动恢复**：打开问题详情时（含从路由恢复），若当前大阶段为 IT 策略规划（`currentMajorStage === 3`），根据「第一个未完成任务」设置 `itStrategyPlanViewingSubstep`（task10→0, task11→1, …），使刷新后停留在当前任务页而非总是回到 Task10。工作区滚动位置：在 `pagehide` 时若当前在问题详情且存在 `.problem-detail-workspace-scroll`，将其 `scrollTop` 存入 sessionStorage（key: `problemDetailScroll_${item.createdAt}`）；再次打开同一问题详情并执行 `renderProblemDetailContent` 后，在双 rAF 内读取该 key、恢复滚动位置并删除该 key。

#### 5.6.1 task10 完工 → task11 任务通知（实现门控，FE-20260328-01）

- **触发链**：用户在「【角色与权限模型推演】是否视为完成？」上点击「已完成」→ 在线模式 `refreshProblemDetailBundleFromBackend` 合并案例态 → `requestAnimationFrame` 中 `showNextTaskStartNotification()`（若 `ensureTask10RefreshNotificationIfNeeded` 未吞掉）。
- **不得误拦 task11**：下一任务为 task11 时，判定「task10 侧是否仍有未决聊天块」须满足：
  1. 若 **`isTaskCompleted(item, 'task10')` 已为真**，不再因聊天数组中更靠前的陈旧 `rolePermissionAuditIntentBlock` / `taskCompletionConfirmBlock(task10)`（`confirmed: false`）而拦截任务启动通知（与 §5.1「任务完工确认优先」一致：以案例完成态为准）。
  2. 否则，仅看 **`rolePermissionAuditIntentBlock` 的最后一条**与 **`taskCompletionConfirmBlock(task10)` 的最后一条**：任一条存在且未确认，则仍拦截；避免 `some()` 命中历史重复插入的未确认副本。
- **刷新门控**：`ensureTask10RefreshNotificationIfNeeded` 在「首个未完成任务仍为 task10」但聊天已出现 **已确认**的 task10 完工确认或 **`taskCompleteBlock(task10)`** 时不再补发 task10 相关块并返回「已处理」，以免阻断紧随其后的 `showNextTaskStartNotification`（典型于在线 bundle 与本地 `markTaskCompletionConfirmBlockConfirmed` 的短窗口不同步）。

- **核心业务对象推演全部确认**：当（1）自动顺序执行跑完所有环节，或（2）刷新页面且所有 session 已有输出但仍有未确认的环节卡片时，聊天区展示提示块「所有环节的核心业务对象推演已经结束，是否全部确认？」与按钮「全部确认」。用户点击后，所有环节反馈卡片视为已确认，过程日志中对应环节的 JSON 由「输出」变为「确认」，并弹出「是否视为完成」。
- **角色与权限确认内容卡片**：聊天区中角色与权限模型推演结果卡片支持删除（带删除按钮）；点击删除后，该条消息从沟通历史移除，工作区根据「最新已确认」结果重绘，若删除的为当前展示用卡片则工作区对应内容同步清除。
- **角色与权限确认 → 工作区渲染**：用户点击「角色与权限模型推演」提炼内容块的「确认」按钮后，系统将每个环节的推演内容渲染到对应工作区卡片中（如：环节「客户需求对接与订单获取」的内容加载到工作区 / 市场与销售 / 环节：客户需求对接与订单获取 卡片内）；同时自动切换到 IT 策略规划大阶段、角色与权限子任务视图，并滚动到工作区，便于用户查看各环节填充结果。
- **工作区 Task10 结构**：一级卡片（大阶段）左边缘与任务按钮栏「角色与权限模型推演」按钮左边缘对齐（通过 `.problem-detail-role-permission-wrap` 与 `.problem-detail-substeps` 一致的左右 padding）；环节子卡片以嵌入形式排在大阶段卡片内，左侧有竖线 + 每条环节前横枝的树形引导线；阶段卡片 body 顶部、底部与环节子卡片之间保留空隙。

> 后续 IT 策略规划阶段的其他任务（如核心业务对象推演、全局架构设计、环节专项设计、链条串联与闭环、价值回溯与自检）可沿用同一模式：在满足前置条件时自动展示「即将开始 XXX」提示块，由用户确认后启动对应大模型调用与工作区展示。

### 5.7 对话模式（Agent / Ask）

问题详情对话区支持两种模式，通过输入框左上角的下拉选择器切换（Cursor 风格，图标 + 文本 +  chevron）：

| 模式 | 说明 |
|------|------|
| **Agent** | 与大模型完整联动：意图提炼后执行修改/执行任务会更新工作区；讨论、修改等会写入沟通历史；对话标题栏显示**「当前任务：【当前任务名称】」**，任务名以蓝底白字标签突出显示；**点击该标签**可在工作区自动切换到对应大阶段并滚动到对应内容卡片（需求理解/工作流对齐/ITGap/IT策略规划及子步骤卡片）；输入框 placeholder 为「输入消息或执行操作…」 |
| **Ask** | 仅支持查询与讨论：用户输入只触发查询/讨论，不更新工作区，不写入沟通历史；意图为「修改」「执行」时展示提示「当前为 Ask 模式，仅支持查询与讨论。请切换至 Agent 模式」；对话标题栏显示**「询问讨论模式」**；**输入框**：底色为淡绿色（#e8f5e9）、字体为深蓝色（#0d47a1）、占位符为「您想了解本项目的什么信息？」，以与背景色形成反差、便于识别 |

- **消息标记**：Ask 模式下产生的消息带 `askMode: true`，`js/communication-history.js` 的 `getCommunicationsByTask` 会排除这些消息，故不出现在沟通历史中。
- **发送按钮**：大模型处理期间（意图提炼、查询、讨论、修改等）发送按钮禁用，处理完成后恢复。
- **上下文截断提示**：Ask 模式查询时，`buildAskModeProblemContext` 将各数据块限制在 `ASK_CONTEXT_MAX_PER_BLOCK`（20000 字符）内；若任一数据块被截断，则在 LLM 回答展示后，聊天区追加系统提示「上下文长度已经超过最大截断值，查询信息不一定准确。」

### 5.8 确认 / 修改 / 讨论 与任务完工确认流程

对所有大模型返回的提炼内容块（如企业基本信息、BMC、需求逻辑、价值流、意图提炼、角色与权限、全局 ITGap/角色汇总设计、修改/讨论后的新提炼块等），在「确认」按钮旁提供**「修改」**与**「讨论」**按钮（样式与「重做」按钮一致：灰字、透明底、描边）。

- **修改**：用户点击「修改」后，（1）**不**向当前任务的过程日志推送任何内容；（2）在聊天区追加系统提示「请描述您的修改意见（输入后发送）」；（3）用户输入并发送后，系统以**当前任务的时间线历史**为上下文 + 用户反馈，调用大模型重新生成；（4）大模型回复作为新的提炼内容块（`modificationResponseBlock`）展示，同样带确认/修改/讨论按钮。用户发送的修改意见以「修正」标签写入过程日志。
- **讨论**：用户点击「讨论」后，在聊天区追加系统提示「请描述您想讨论的问题（输入后发送）」；用户输入并发送后，以当前任务时间线 + 用户输入调用大模型，回复作为新的内容块展示。**Task2（商业画布）** 的讨论为独立「BMC 讨论模式」：以当前 base BMC 数据、讨论开始后的历史轮次、用户当前输入组装四段式提示（system 为 BMC 讨论专用提示词），调用 `runBmcDiscussionTurn`；时间线中每次用户发言推送「用户讨论」、每次系统回复推送「LLM-查询」备注「大模型讨论应答」；讨论回复块下提供「继续讨论」「重新生成」，点击「重新生成」则基于最新 BMC 与讨论历史重新生成整份 BMC 并结束讨论；对话区标题栏右上角在讨论模式下显示讨论动画，结束讨论后消失。

用户点击「确认」后触发统一流程：

1. **过程日志更新**：按该内容块的时间戳及「确认」标签，在当前任务的过程日志时间线中更新/展示对应条目。
2. **任务完工确认块**：在聊天区发送任务完工确认内容块：「【当前任务名称】是否视为完成？」，下方提供两个按钮：
   - **已完成**：（1）在当前任务的过程日志时间线中增加一条「任务完成」类型的内容块（**仅写入过程日志，不在聊天区展示**），展示内容按任务区分（如端到端事务流构建为「用户确认端到端事务流构建」、task8 为「用户确认 IT设计补齐」或历史文案「用户确认全局 ITGap 分析」等），标签为「任务完成」；（2）将当前问题的**当前状态推进到状态机下一状态**（如标记本任务完成、更新 `completedStages` / `workflowAlignCompletedStages` / `itGapCompletedStages` / `currentMajorStage` 或 `completedTaskIds`，并刷新工作区与进度）；（3）**弹出下一任务的开始通知**；（4）确认块上按钮置为已选/禁用。
   - **请修改**：在聊天框中追加系统消息「您要对【任务名称】的成果做什么修改？请回复修改意见要有明确的修改动因及修改意见。」；确认块上按钮置为已选/禁用。「请修改」按钮的视觉样式与「重做」按钮一致（灰字、透明底、描边）。

上述流程在问题详情聊天区所有带「确认」的提炼内容块上统一生效（任务启动类「确认」除外）。**端到端事务流 JSON 卡片**与其它提炼块一致：点击「确认」后仅更新过程日志中该条为「确认」并推送「是否视为完成」块，**不**在此刻推进任务状态；仅当用户点击「已完成」后才写入「任务完成」条目并推进当前任务至 **task8（IT设计补齐）**。
