## 1. 用户意图类型

系统支持四种用户意图类型，代码与展示名称的对应关系如下：

| 意图代码 (intent) | 展示名称 | 说明 |
|-------------------|----------|------|
| `query` | 简单查询 | 用户查询当前问题中的具体内容 |
| `modification` | 反馈修改意见 | 用户提出对页面内容的修改需求 |
| `execute` | 执行操作 | 用户执行某任务（如重新构建需求逻辑等） |
| `discussion` | 讨论请教 | 用户针对当前问题进行延展性讨论或请教 |

### 代码中的映射

```javascript
const intentLabels = {
  query: '简单查询',
  modification: '反馈修改意见',
  execute: '执行操作',
  discussion: '讨论请教'
};
```

## 2. 解析提示词

**触发入口**：问题详情页聊天区，用户输入消息后点击发送  
**函数**：`extractUserIntentFromChat(text, context, options)`  
**用途**：提炼用户输入的意图类型，结合沟通历史与页面内容结构定位到具体任务与字段。

**当前任务与「不对」按钮**：
- 默认：系统根据沟通历史推断「当前任务」，并在 prompt 中传入 `currentTaskHint`，大模型优先考虑该任务与用户意图的关联。
- 意图卡片除「确认」外，还有「不对」按钮。用户点击「不对」时，系统重新调用 `extractUserIntentFromChat` 并传入 `globalScope: true`，大模型在【任务列表】中全局搜索，不受当前任务预设限制。

### System Prompt

```
你是一个数字化问题跟进对话的意图分析助手。用户会在聊天区输入消息，请结合【沟通历史】和【当前页面内容结构】提炼意图，从上下文中搜索最为匹配的内容单元，协助定位到对应的页面位置。

【任务列表】
${tasksDesc}

【输出格式】
{
  "taskId": "task1",
  "taskName": "企业背景洞察",
  "stage": "需求理解",
  "intent": "query" | "modification" | "execute" | "discussion",
  "queryTarget": "用户想查询的具体内容，仅当 intent 为 query 时填写",
  "discussionTopic": "用户想请教或讨论的具体话题，仅当 intent 为 discussion 时填写",
  "queryValueStreamLevel": "step" | "stage" | "card",
  "queryValueStreamTarget": "环节名或阶段名",
  "modificationTarget": "用户想修改的具体内容或目标，仅当 intent 为 modification 时填写",
  "modificationField": "具体要修改的字段名称，仅当 intent 为 modification 且能明确到具体字段时填写",
  "modificationValueStreamLevel": "step" | "stage" | "card",
  "modificationValueStreamTarget": "环节名或阶段名",
  "modificationClear": true | false,
  "modificationNewValue": "用户希望修改成的具体内容",
  "executeTaskId": "task2",
  "executeTaskName": "商业画布加载",
  "summary": "一句话概括用户意图"
}

【可修改字段参考】（modificationField 应使用以下精确字段名之一）
- 初步需求：客户名称、客户需求或挑战、客户IT现状、项目时间要求
- 客户基本信息：公司名称、信用代码、法人、成立时间、注册资本、是否上市、上市地、经营范围、核心资质、官方网站
- BMC：行业背景洞察、客户细分、价值主张、渠道通路、客户关系、收入来源、核心资源、关键业务、重要合作、成本结构、业务痛点预判
- 需求逻辑：行业底层逻辑与竞争共性、初步需求与商业模式的"因果关联"、需求背后的深层动机、逻辑链条总结

规则：
1. 结合【沟通历史】理解对话脉络，从【当前页面内容结构】中搜索与用户输入最为匹配的内容单元（字段名、环节名、阶段名等）。
2. taskId/taskName/stage：根据用户消息及沟通历史推断当前沟通涉及的任务及阶段，从上述任务列表中选择最相关的。
3. intent：简单查询(query) / 反馈修改意见(modification) / 执行操作(execute) / 请教讨论(discussion)
4. 若 intent=discussion：用户针对当前问题的各种专题进行延展性讨论或请教时填写。判断用户讨论话题与哪个任务最为相关，填写 taskId；填写 discussionTopic 概括讨论话题。
5. 若 intent=query，填写 queryTarget；若涉及价值流图，从【当前页面内容结构】中匹配环节名/阶段名，填写 queryValueStreamLevel 和 queryValueStreamTarget
6. 若 intent=modification：必须判断 modificationClear。仅当用户明确指定了「把什么改成什么」（具体修改对象+修改后的值）时填 true，否则填 false。若用户只说「想修改」「改一下」等未明确具体内容，填 false。modificationNewValue 仅当 modificationClear 为 true 时填写用户希望修改成的具体内容。
7. 若 intent=modification 且 modificationClear=true，填写 modificationTarget、modificationField 或 modificationValueStreamTarget；从【当前页面内容结构】中匹配最具体的字段名/环节名/阶段名。
8. 若涉及价值流图：从【当前页面内容结构】的价值流阶段与环节中精确匹配，modificationValueStreamLevel 填 step/stage/card，modificationValueStreamTarget 填匹配到的环节名或阶段名（必须与结构中出现的名称一致）
9. 若 intent=execute，填写 executeTaskId 和 executeTaskName。当用户说「重新进行需求逻辑构建」「重新构建需求逻辑」等时，intent=execute，executeTaskId=task3
10. summary：用一句话概括用户意图
11. 若无法明确推断，相关字段可填空字符串或合理默认值
12. 只返回 JSON，不要有 markdown 代码块包裹
```

### User Message 模板

```
用户输入：${text}

${context}
```

其中 `context` 由 `buildIntentExtractionContext()` 构建，包含【沟通历史】与【当前页面内容结构】。

## 3. 过程日志的提取逻辑

**模块**：`js/communication-history.js`（沟通历史仅做读取与聚合，不写入存储）  
**函数**：`getCommunicationsByTask(createdAt, chats)` — 参数 `chats` 为当前问题的消息数组，由调用方传入（main.js 通过 `getChatsForProblem(createdAt)` 或 `getProblemDetailChats()[createdAt]` 提供）。  
**用途**：将聊天消息按任务分段，返回 `taskId -> communications`，供任务过程日志展示。**当前策略**：过程日志不写入新条目，仅从现有聊天记录中按纳入规则提取；若历史聊天中已有 e2eFlowGeneratedLog、globalItGapAnalysisLog、localItGapAnalysisLog、rolePermissionConfirmedLog 等类型，仍会纳入展示。

### 纳入规则

| 消息类型 | 纳入条件 |
|----------|----------|
| 用户消息 (role=user) | 纳入，但纯「确认」不纳入 |
| 意图卡片 (intentExtractionCard) | intent=query：不纳入；intent=discussion：不纳入（意图卡片本身不纳入，用户消息与系统回复已单独处理）；其他 intent：仅当 `confirmed=true` 时纳入 |
| 其他系统消息 (basicInfoCard、bmcCard、requirementLogicBlock) | 纳入 |
| valueStreamCard（价值流图 JSON 卡片） | **不纳入**过程日志时间线；task4 仅保留 **task4LlmQueryBlock**（**LLM-查询**，双子卡输入/输出）纳入；每轮生成后**先**刷新工作区再写入该块，标题栏右侧备注：**忠实还原策略价值流生成**（Mirror）、**架构加固策略价值流补充**或含阶段名（分阶段加固）。卡片含 data、logicText，供工作区展示。 |
| 请教讨论的系统回复 (带 _taskId) | 纳入 |
| unsatisfiedBlock | **不纳入**（用户点击「修正」时不再向过程日志推送） |
| e2eFlowExtractStartBlock | 仅当 `confirmed=true` 时纳入 |
| e2eFlowJsonBlock | 仅当 `confirmed=true` 时纳入 |
| e2eFlowCompressionBlock | 纳入（端到端事务流全景观提炼压缩，标签 LLM-压缩，含 llmInputPrompt/llmOutputRaw/llmMeta） |
| e2eFlowGeneratedLog | 纳入（已不再写入，仅历史存在时展示） |
| globalItGapStartBlock | 仅当 `confirmed=true` 时纳入 |
| globalItGapAnalysisCard | 仅当 `confirmed=true` 时纳入 |
| globalItGapAnalysisLog | 纳入（已不再写入，仅历史存在时展示） |
| localItGapStartBlock | 仅当 `confirmed=true` 时纳入 |
| localItGapSessionsBlock | 纳入（含 sessions 数据） |
| localItGapContextBlock | 纳入（价值流图 json / 全局 ITGap 分析压缩 json（优先，缺失回退全局 ITGap 分析 json），仅入过程日志不入聊天区） |
| localItGapAnalysisCard | 仅当 `confirmed=true` 时纳入（含 analysisJson、llmMeta） |
| localItGapAnalysisLog | 纳入（已不再写入，仅历史存在时展示） |
| localItGapCompressionIntentBlock | 纳入（角色汇总设计压缩确认块，未确认为「输出」、已确认为「确认」） |
| localItGapCompressionBlock | 纳入（压缩结果，标签「压缩」+ 环节名，含 compressedJson、llmMeta） |

### 讨论意图的特殊处理

- intent=discussion 且 confirmed 时：将用户消息移动到对应任务下，并插入一条 `speaker: '系统提炼'` 的提炼条目，content 为 `{ role, type: 'intentExtractionCard', content: '讨论请教', data, userText, timestamp }`。
- 其他已确认的意图卡片：以 `speaker: '系统大模型'` 纳入，content 为完整 payload（含 role、content、type、data、timestamp 等）。

### 不纳入的条目

- 查询意图 (query)：用户查询内容及系统返回的意图卡片均不纳入。
- 未确认的意图卡片：除 discussion 外，未确认的意图卡片及其触发的用户消息不纳入；discussion 会移除用户消息并插入系统提炼条目。

## 4. 过程日志的显示逻辑

### 4.1 展示位置

1. **任务追踪详情**：`renderTaskTrackingDetail()`，任务过程日志以列表形式展示。
2. **问题详情历史面板**：`renderProblemDetailHistory()`。每个任务展开后包含**两个可折叠 Tab**：
   - **任务详情**：展示归属阶段、任务目标、评估标准、输入、动作、输出反馈、任务状态。
   - **过程日志**：以时间线形式展示该任务下的沟通记录；每条时间线条目的标题栏由**时间戳 + 日志类型标签**构成（见 4.5）。

### 4.2 用户意图提炼标题规则

所有对用户信息提炼的内容块（即 content 中 `type === 'intentExtractionCard'` 且存在 `data.intent` 的条目），标题统一显示为：

```
用户意图提炼：[意图展示名称]
```

其中 `[意图展示名称]` 由 `intentLabels[intent]` 映射得到，例如：

- `用户意图提炼：简单查询`
- `用户意图提炼：反馈修改意见`
- `用户意图提炼：执行操作`
- `用户意图提炼：讨论请教`

### 4.3 判断逻辑

```javascript
let titleLabel = c.speaker;
try {
  const parsed = typeof c.content === 'string' ? JSON.parse(c.content) : c.content;
  if (parsed?.type === 'intentExtractionCard' && parsed?.data?.intent != null) {
    const intentLabel = intentLabels[parsed.data.intent] || parsed.data.intent || '—';
    titleLabel = `用户意图提炼：${intentLabel}`;
  }
} catch (_) {}
```

无论原始 speaker 为「系统提炼」还是「系统大模型」，只要 content 为意图提炼卡片，均按上述规则显示标题。

### 4.5 过程日志中的日志类型标签（问题详情历史面板）

过程日志 Tab 内，每条时间线内容块的标题栏统一为**时间戳 + 日志类型标签**。标签右侧的**备注**（环节名、`contextLabel`、session 计划说明等，类名 `problem-detail-history-timeline-step-name`）为**与时间线圆点同色**的蓝色；超过 **15 字**时标题栏只显示前 15 字 + `...`，全文见 `title` 悬停。日志类型由 `getCommunicationLogType(c)`（js/communication-history.js）根据条目内容推断。**注意**：`taskCompleteBlock` 的判定必须在 `speaker === '用户'` 之前，否则会被误判为「输入」。

| 日志类型 | 判定条件 |
|----------|----------|
| 修正 | 用户消息带 `_logType === 'modify'`（用户点击「修正」后发送的修改意见） |
| 任务完成 | 消息类型为 `taskCompleteBlock`（用户点击「已完成」后写入，仅过程日志，不在聊天区展示） |
| 输入 | 用户发言（`speaker === '用户'`，且非上述类型） |
| 讨论 | 意图为讨论（`intent === 'discussion'`）或系统提炼的讨论（`speaker === '系统提炼'`） |
| 修改 | 意图为修改（`intent === 'modification'`） |
| 上下文 | 意图为查询或执行（`intent === 'query'` 或 `intent === 'execute'`）的意图提炼卡片；taskContextBlock、globalItGapContextLog、localItGapContextLog、localItGapContextBlock、coreBusinessObjectContextBlock、globalArchitectureContextBlock 等 |
| LLM 压缩 | 消息类型为 `localItGapCompressionBlock`（角色汇总设计按环节压缩）、`globalItGapCompressionBlock`（全局 ITGap 确认后的架构约束底座压缩）或 `e2eFlowCompressionBlock`（端到端事务流全景观提炼压缩）；时间线标签「LLM-压缩」，展开区为输入/输出子卡片（样式同 LLM-查询） |
| 确认 | 其余（各类系统确认、意图卡片确认等） |

样式：在 `.problem-detail-history-panel` 作用域内，**标签类文案统一字号**：由 CSS 变量 `--history-label-fs`、`--history-label-lh` 等控制（含顶部汇总、`任务详情`/`过程日志`/`任务Skill` Tab、时间线标题行时间戳、右侧耗时/token、展开区元信息、LLM-查询子卡标题等）；**日志类型**仍用 `.problem-detail-history-log-type-tag` 及按类型区分的 class（`input` / `output` / `confirm` / `modify` / `discuss` / `context` / `complete` / `compress` / `llm-query` / `llm-compress` 等）区分色相；类型标签 padding 由 `--history-tag-pad-*` 控制以更紧凑。**任务Skill** Tab 的「当前最新版本」黄卡、节点内 Diff/更新版双子卡配色与数据源规则见 [数字化问题跟进阶段设计.md](./数字化问题跟进阶段设计.md) §0.6。详见 `styles.css`。

### 4.6 时间线备注（耗时，输入 token，输出 token）

所有时间线内容卡片备注统一为三项、顺序一致：**耗时，输入 token，输出 token**。

- **输入卡片**：耗时为 0，输出 token 为 0，输入 token 为**后续**大模型调用返回的 **prompt_tokens**（取自下一条消息的 llmMeta.usage）。
- **输出/确认卡片**：耗时为**大模型返回的 durationMs**，输入 token 为 0，输出 token 为大模型返回的 **completion_tokens**。
- **压缩卡片**：耗时为该次大模型返回耗时，输入 token 为该次调用的 **prompt_tokens**，输出 token 为该次调用的 **completion_tokens**。
- **顶部汇总与任务标题行**：按上述规则累计各条目的耗时、输入 token、输出 token（输入卡片贡献输入 token，输出/确认贡献耗时与输出 token，压缩卡片贡献三项）。
- **角色汇总设计输入块**：LLM 返回后会对对应的 `localItGapInputBlock` 补写 `llmMeta`（含 usage）；时间线显示时，输入卡片的「输入 token」取自**下一条**消息的 prompt_tokens。

### 5.0 统一任务启动通知

系统对每个任务采用**统一的任务启动通知**，在聊天区以同一格式提醒用户即将开始的任务，用户点击确认后直接执行该任务的大模型调用或流程逻辑。

| 项目 | 说明 |
|------|------|
| 消息类型 | `taskStartNotification`（字段：`taskId`、`taskName`、`timestamp`、`confirmed`） |
| 展示内容 | 「任务通知：我即将开始【任务名称】任务」 |
| 确认按钮 | 与内容卡片一致（`btn-confirm-task-start`、`btn-confirm-primary`），禁用后显示「已确认」 |
| 确认后动作 | 按 `taskId` 分发：task1 提示补充基本信息；task2 执行 BMC 生成；task3 需求逻辑构建；task4 价值流生成；task5 IT 现状标注；task6 痛点标注；task7 进入 ITGap 并展示端到端事务流 JSON；task8 全局 ITGap 分析；task9 生成角色汇总设计 sessions 并开始逐环节分析；task10 角色与权限推演；task11~15 切换至对应 IT 策略子步骤并刷新工作区 |

**触发条件**：

1. **上一任务结束后**：当用户完成某一任务（如确认基本信息、确认 BMC、确认需求逻辑等）并**点击任务完工确认块的「已完成」按钮**后，系统在下一帧自动展示「当前第一个未完成任务」的任务启动通知。**重要**：若出现任务完工确认块（「【任务名】是否视为完成？」），下一任务通知**必须**等用户点击「已完成」后才弹出，不得在确认块出现时立即弹出。
2. **页面刷新**：在问题详情页任意 tab 下刷新浏览器时，系统根据当前问题状态计算第一个未完成任务，若聊天中尚无该任务的 `taskStartNotification`，则自动展示该任务的任务启动通知。

**去重**：若聊天记录中已存在同一 `taskId` 的 `taskStartNotification`（无论是否已确认），则不再重复插入。

**过程日志**：`taskStartNotification` 当前不纳入任务过程日志（与 itGapStartBlock 等入口块类似）。
